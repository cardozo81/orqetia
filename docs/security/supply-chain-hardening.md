# Software supply-chain hardening

**Status:** M9 policy  
**Issue:** #152  
**Lifecycle:** DEVELOPMENT; this policy does not declare RC or a release.

## Locked dependency inventory

`uv.lock` is the authoritative dependency inventory for Python builds. The
project and development dependency ranges in `pyproject.toml` define intent;
the lockfile defines the concrete dependency graph used by CI.

Do not infer the deployed dependency set from an unlocked `pip install`.

## Reproducible SBOM

Generate the CycloneDX 1.6 SBOM directly from the lockfile:

```bash
revision="$(git rev-parse HEAD)"
python scripts/generate_supply_chain_artifacts.py generate \
  --lock uv.lock \
  --pyproject pyproject.toml \
  --source-revision "$revision" \
  --output-dir .tmp/supply-chain
sha256sum .tmp/supply-chain/orqetia.cdx.json
```

For the same `uv.lock`, `pyproject.toml` and source revision, generated bytes
must be identical. The SBOM intentionally omits generation timestamps and does
not read runtime environment variables.

The SBOM includes runtime-direct, dev-direct and transitive locked packages.
A source-distribution/wheel SHA-256 from `uv.lock` is included when available.

## Provenance

The same command emits an in-toto Statement v1 with a SLSA provenance v1
predicate. The provenance subject is the generated SBOM digest. Resolved
materials include:

- the exact Git commit SHA supplied to the command;
- the exact `uv.lock` SHA-256.

The statement is build metadata, not a public release signature. Release signing
or attestation publication requires the lifecycle decision defined by #46.

## Generated-artifact secret boundary

Supply-chain artifact generation may read only the lockfile, project metadata and
the explicit source revision. It must not copy environment variables, database
DSNs, OIDC secrets, provider credentials, GitHub tokens or application payloads
into SBOM/provenance.

CI must generate these artifacts in a temporary directory. They are evidence for
the gate, not an alternate secret store.

## GitHub Actions

Repository security policy requires:

- external GitHub Actions pinned to full immutable commit SHA;
- `persist-credentials: false` for checkout;
- explicit workflow permissions;
- no `pull_request_target`;
- no pipe-to-shell bootstrap.

#53 owns the generic repository checker. #152 reuses that checker instead of
creating a divergent action-pinning implementation.

## Vulnerability and reachability triage

The dedicated supply-chain gate audits the exported, hashed locked dependency set
with the already locked `pip-audit` tool.

Public CI output must not dump vulnerability descriptions, exploit instructions,
proofs of concept or secrets. A failing audit may expose only the affected
package/version, dependency class and whether a fixed version is available.

Dependency class is triage evidence, not proof that a transitive dependency is
unreachable. A vulnerable transitive package must be traced through the lockfile
graph before it can be accepted as non-reachable.

## Emergency dependency CVE procedure

1. Confirm the finding against the exact locked version.
2. Classify it as runtime-direct, dev-direct or transitive and identify the
   shortest dependency path that introduces it.
3. Prefer the smallest compatible fixed version. Avoid unrelated bulk upgrades.
4. Update the lock with a targeted command such as
   `uv lock --upgrade-package <package>`.
5. Run `uv lock --check`, the supply-chain gate and the isolated tests for the
   affected boundary.
6. Regenerate SBOM/provenance and compare their hashes.
7. Record package/version, affected boundary, fix version and validation result.
   Do not publish exploit details while remediation is active.
8. If no compatible fix exists, fail closed for an exploitable runtime path or
   document a time-bounded exception with compensating controls and owner.
9. Roll back the dependency change if the fix breaks the affected boundary;
   never restore a known exploitable version without an explicit exception.

No provider call or paid security service is required by this procedure.

## Gate

The isolated `Supply chain` workflow must prove:

- lockfile is internally consistent;
- two independent generations produce byte-identical SBOM/provenance;
- provenance digests match generated artifacts and source revision;
- repository security baseline still enforces pinned actions/explicit
  permissions;
- dedicated supply-chain tests pass;
- vulnerability audit uses the hashed locked export without printing exploit
  detail.
